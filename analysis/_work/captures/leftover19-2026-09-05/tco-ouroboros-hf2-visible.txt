Compute profile and cost This run was configured for maximum answer quality, not for cost efficiency, and the gap to the in-context-learning rows is real compute rather than an accounting artifact: this run ICL · Claude Sonnet 4.6 cost per full pass (six tasks) $440.65 $30.43 cost per question $1.46 $0.10 LLM calls per question 11.4 ~1 mean prompt per call 112,550 tokens not reported An ICL row answers a question with essentially one model call. Ouroboros runs an agent loop per question, reading and rewriting its persistent memory, calling tools, then a blocking review pass that can send the answer back for revision. With context_mode=max , each of those calls carries a large context. Over the campaign that is 2.31 B prompt tokens against 24.7 M completion tokens (94:1): the bill is almost entirely input. At list price those prompt tokens alone would be ≈$6,900; prompt caching brings the actual spend to $2,443.93, so caching already absorbs about two thirds of it. The practical reading is that context size × loop depth, not the review itself, sets the price: a configuration with adaptive rather than maximal context should land far cheaper, and would be a separate point on the quality/cost curve. Figures: the full campaign (6 baselines + 30 rollouts) cost $2,486.47 ; the per-pass number above is the mean rollout cost per task summed over the six tasks, the same formula the scorer applies to every system. Independently verified against the engine's own ledger in this dataset, with 20,523 LLM calls totalling $2,443.93 ( layer3_server_logs/*/logs/events.jsonl ), which matches the sum of per-task cost records to within 0.01%, so nothing is double counted; the published figure sits 1.7% above the raw ledger, i.e. it overstates rather than understates our spend. Methodology Schedule and arms The benchmark's default schedule was run in full through the official run_benchmark.py run-all entry point: 1 stateless baseline per task: the same agent with memory disabled, answering each question independently. This is the per-system reference for normalized_gain . 5 stateful rollouts per task ( run_index 0–4). Each rollout is a permutation of the question order produced by the task's own prepare_run(run_index) , so a system cannot profit from one lucky ordering. Two tasks differ by design: sales_prediction is a replicate (fixed order) and blind_spectrum_monitoring varies the generated scan rather than the question order. Within a rollout the agent sees questions strictly in sequence and keeps whatever it learned; reset() between rollouts is total, with fresh container state and fresh memory. What the agent is, per question Each benchmark question becomes one Ouroboros task running inside an isolated Ouroboros server in its own Docker container (own data root, own state). The agent reaches the benchmark only through the official respond() / observe() cycle, brokered by a small local HTTP shim; task definitions, datasets and reward functions stay host-side and are never visible to the agent. Answers are returned through an explicit final-answer delivery step rather than scraped from chat text. The continual-learning mechanism under test is Ouroboros's native persistent memory : a fresh conversation per question, but a memory store (identity, scratchpad, knowledge artifacts) that the agent reads and rewrites with its own tools and that persists across questions within a rollout. layer3_server_logs/*/memory/ in this dataset is exactly that store, captured as it evolved. Configuration One model fills every slot (main, heavy, light, review, and vision), so there is no hidden ensemble; credentials of undeclared providers are blanked inside the container. knob value runtime mode pro reasoning effort task high , review low context mode max self-review mandatory, blocking, task review required improvement passes pinned to 1 LLM safety supervisor off subagent delegation off (depth 0 + schedule_subagent excluded); single-agent run core evolution disabled web search / vision tools disabled per-task cost cap $50 The blocking review loop is the main reason this run costs more than the ICL rows: every answer is critiqued and, if the reviewer objects, revised before delivery. Parallelism Six task subprocesses ran concurrently; within each task up to 6 rollout/baseline workers ran in parallel ( summary.max_workers = 6 ); each engine server used an internal pool of 3 (with delegation disabled this is intra-task concurrency, not extra agents). Rollouts share no state, so parallelism cannot leak information between arms. Known artefacts of this run Poker auto-resolution: exactly 16 of 120 outcomes in the baseline and in each rollout (96 total) were closed as a side effect of another question's task.step() without agent interaction, so no cost or latency rows exist for them. All officially-scored outcomes are preserved. Continuity metadata: summary.system.continuity.mode reads fresh_per_turn ; the accurate semantics are "fresh conversation per question, persistent native memory per rollout" because the schema field predates this memory model. Reproducing The submission PR carries the adapter ( src/systems/ouroboros/ ), its METHODOLOGY.md with the exact non-secret env block, the contract tests and a runnable recipe. When rescoring, note that the fixed reference baseline comes from the icl-gpt-5.4 artifacts, so any --run filter must include that run (the default set does). Dataset layout path contents layer2_runner_traces/<task>/traces/<ts>_run-all/ benchmark-runner-side traces: baseline.json.gz + run_000{0..4}.json.gz per task, with per-question prompts, responses, rewards, latency and usage events as recorded by run_benchmark.py layer2_manifests/<session>/ per-server-session bridge manifests: run_manifest.json (model, mode, argv) and turns.jsonl (the respond/observe turn log) layer3_server_logs/<env>/logs/ engine-internal logs of each isolated server: chat.jsonl , events.jsonl (every LLM round + usage), progress.jsonl , tools.jsonl (every tool call), supervisor.jsonl , server.log layer3_server_logs/<env>/memory/ the agent's persistent memory as it evolved during the rollout layer3_server_logs/<env>/task_results/ per-task result records including review traces layer3_server_logs/<env>/state/skills/ skill lifecycle state (review, grants, enablement) Each obo_dockerclbench_* directory is one isolated server instance (315 of them). Files larger than 1 MB are gzipped. Together these layers let a reviewer audit the run end-to-end: confirm answers were produced by the agent rather than leaked from the harness, count model calls, recompute cost from the usage records in events.jsonl , and watch memory accumulate across a rollout. Redaction Applied deterministically before upload; no score-bearing value was modified: All credential values (API keys, tokens) → <REDACTED:...> ; config files ( settings.json ) are excluded from the dataset entirely. Absolute local paths → placeholders ( <BENCH_ROOT> , <ENGINE_RUNS_ROOT> , <RUN_ROOT> , <ENGINE_CLONE> , <VENV> , <HOME> , <DATA_ROOT> , <USER> ), using the same map used for the artifacts in the PR. The staged tree was then re-scanned twice: a fixed-string search for every known credential, and a regex sweep for credential prefixes across all files including gzipped ones, with zero hits.
